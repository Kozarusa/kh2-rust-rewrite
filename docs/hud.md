# HUD (WP-4B phase 1 and WP-4B2 phase 2)

Status of what the in-battle HUD uses, where it comes from, and what is still open. "Verified" means read from the game's code or data and checked against the running result; "inferred" means a reading that fits the data but was not confirmed in code.

Decomp addresses are for the USA executable (SLUS_210.05), local study copy only.

## Files used (all read from the disc at run time)

- `field2d/us/<world>0field.2dd` (for example `tt0field.2dd`; `zz0field.2dd` is the fallback; the loader is at 0x13a7e8, format string at 0x378d78). A BAR of (IMGD type 24, SEQD type 25) pairs in this order: `fiel` (lock-on reticle, text banners, munny digits), `gaug` (Sora's gauges, target gauge, drive gauge pieces), `mapj` (minimap frame), `miss` (mission marks). The pair accessors are 0x13a980 (image) and 0x13a998 (sequence), the loader 0x13a8a8. Verified.
- `field2d/us/<world>0command.2dd` (loader 0x13a6d0, format strings 0x378d38 and 0x378d58: `<world><variant>command.2dd`, the variant a byte of the area record, `FUN_001935e8`; Twilight Town has variants 0 to 6, most worlds 0 and 1). One `comw` pair (IMGD 512x256, SEQD with 98 groups): the command menu. Pair accessors 0x13a9b0 and 0x13a9c0. This port always uses variant 0 and falls back to `zz0command.2dd`. Verified.
- `obj/P_EX100.apdx`, BAR entries `face` (IMGD + SEQD): Sora's portrait inside the ring (member resource +0x7b0, tag "face", fetched by 0x16b998). Verified.
- `msg/us/sys.bar`, `msg/us/fontimage.bar`, `msg/us/fontinfo.bar` (paths at 0x37ad50, 0x37b6f0, 0x37b6d8): the text system, see "Text". `03system.bin` entry `ftst`: text colours.
- Formats: IMGD per OpenKH `docs/kh2/file/type/image.md`; SEQD per OpenKH `OpenKh.Kh2/Sequence.cs` (header, sprites 0x2c bytes, sprite parts 0x14, sprite groups 4, animations 0x90, animation groups 0x24). Layout checked against section sizes of real files. The pixel order of swizzled IMGDs (flag bit 2) is the PSMCT32 upload canvas; decoded with the same GS tables as model textures. Verified on real files (images look right). Every 8-bit IMGD, swizzled or not, reads its palette in the GS CSM1 order (pixel value bits 3 and 4 swapped); see "Sora's portrait (WP-FIX-8)".

## Sequence player rules (verified in code)

- Frame stepping: 0x2378a0. A group starts at frame 0; one logic tick adds 1.0 (times a speed that is 1.0 for all HUD objects found). When the frame reaches the group end it restarts at the group's `loop_start` field; a non-zero `loops` count stops after that many plays and holds the last frame; zero loops forever. Group length: 0x236800 and 0x2367a8 (largest animation end, minus one for animations with flag 0x8000, capped by the group's explicit end). The tick rate (60 Hz) is inferred.
- Animation evaluation and drawing: 0x2379a8 (draw), 0x236cf8 (anchor), 0x235450 (quad build). An animation draws when `start <= frame <= end` (not on the end frame with flag 0x8000). Interpolation t = (frame - start) / (end - start); without flag 1 the time curve is a cubic Bezier with control values `curve_y_start`, `curve_y_end`. Translation and pivot are integer lerps; pivot is added to the sprite part before scale and rotation; scale = Scale x ScaleX (or ScaleY), rotation is the 2x2 reduction of the x, y, z Euler matrix at 0x2346a8; bounce adds `amplitude * sin|cos(t * pi * count)` (flag 8 selects cosine, flag 0x10 disables). Flags seen: 1 linear, 2 anchor, 4 nearest filtering, 0x20 no rotation, 0x40 no scale, 0x80 colour steps, 0x400 no colour, 0x4000 no pivot, 0x8000 exclusive end.
- Colour: per-channel `(sprite colour * animation colour) >> 7` (0x80 is 1.0), 0x230738. Blend preset from the animation's blend field: 0 alpha, 1 additive, 2 subtractive (GS ALPHA values set up at 0x236598); flag bit 2 selects nearest instead of bilinear texture filtering (TEX1 presets, same function). Zero-width UV sprites stretch one texel column.
- Positions: a HUD object's anchor is the translation (plus rotated pivot) of its first animation flagged 2 at the current frame (0x236cf8). A child is drawn at `parent base + parent anchor + parent offset + own offset` (0x138bf0, 0x138f38). Verified.
- Animation group record (0x24 bytes, accessors at 0x237618 to 0x237698): +0x10 x, +0x14 y (added to a node's position when its flag 0x10 is set, not used by anything ported here), +0x1c passed to the text drawer, +0x20 a width in pixels that row layouts add up (target pips, munny digits). The SEQD parser's names for these are `x`, `y`, `unk1c`, `unk20`. Verified in code (0x237698 callers at 0x1540a0 and 0x15ae80).
- Screen: draw code places vertices at GS (0x7000 + 16 x, 0x7300 + 16 y). The 512x448 screen origin is therefore taken as HUD y = 0 at 16 lines below the top (inferred from 0x7300 versus the usual 0x7200; the draw-environment setup was not found). The 3D projection used for the reticle uses the same offset. Text drawing uses the same constants (0x1a80d8), so text shares the HUD's coordinates.

## Text (WP-4B2)

Crate `kh2-image`, modules `font` and `text`; app side `hud_text.rs`.

### Files

- `msg/us/fontimage.bar`: three type-36 entries. `sys` (0x10000 bytes) is a 512x256 atlas of 4-bit pixels, low nibble first; `evt` (0x20000) is 512x512; `icon` (0xa400) is 256x160 8-bit indices followed by a 1024-byte palette. The loader at 0x1a9190 uploads `sys` to GS page 0 and `evt` to page 0x800 as PSMT4HL (the high-alpha-nibble format) and `icon` to 0x1800 as PSMT8H with the palette at 0x3ffc. Verified.
- The glyph atlases only use the low two bits of each nibble (counts of nibble values in both files: 0 to 3). The game samples them through rows of the icon palette: 0x1a9460 builds TEX0 with palette offset (CSA) 8 plus the page (glyph / glyphs per page) and 1, plus 2 for font mode 3 and 4 for mode 4. Palette row 8 has alpha 0, 42, 98, 128 for pixel values 0 to 3 (0x80 is opaque), row 9 picks by the high two bits, row 10 has 0, 0, 68, 128, row 12 is black at alpha 64, grey 68 at 128 and white at 128. The port reads the rows from the file. Verified (palette decode, and the text looks right).
- `msg/us/fontinfo.bar`: type-2 entries `sys` (280 bytes), `evt` (336), `icon` (60): one advance width in pixels per glyph or icon. The type-25 entry (`md_m`, a SEQD) is the message-window frames (WP-6D, see "Message windows (WP-6D)"). The widths are loaded at 0x1a8ff8 into the font descriptors. Verified (280 = 28 x 10 cells, 336 = 21 x 16, 60 = 10 x 6).
- Glyph cells: font descriptors are built at 0x1a9e60 with 0x1a93e0: font ids 0, 1, 2 and 5 draw the `sys` atlas with 18x24 cells, ids 3 and 4 the `evt` atlas with 24x32 cells; icons are 24x24. The cell heights come from the override at 0x1a9148, which runs for every language but one (the value 1 of `FUN_00105cd8`, taken to be Japanese); the pitch of the glyph rows in the files (24 and 32 pixels) agrees with it. Glyph `g` is at column `g % cols`, row `g / cols` (cols 28 for `sys`, 21 for `evt`). Verified.
- Modes: the font id is also its mode. 0 and 5 plain, 1 drop shadow, 2 outline, 3 plain with the thin ramp (`evt`), 4 the shaded ramp with a skewed draw (`evt`). Mode 1 draws the glyph again 2 pixels right and down first in the shadow colour; mode 2 draws it four times at (-2, 0), (0, 2), (2, 0), (0, -2) (offsets at 0x35ea28; draw code 0x1a8698). The shadow colour is black with alpha 0x60 scaled by the text alpha (0x1a8de0 sets 0x60000000, 0x1a8ce0 scales it). Verified for 0 to 3; mode 4 is drawn here as a plain glyph with its palette row (the skewed draw at 0x1a9818 is not ported).

### Message table and byte code

- `sys.bar` entry `sys` (type 2): u32 version (1), u32 count, count x (u32 id, u32 offset), texts at the offsets. Table fields that name text (`Cmd.MessageId`, `Item.Name`) have bit 15 set; the file's id is the low 15 bits (the game's lookup is 0x190c40, with a fallback to message 0x8adc). 2,869 messages in the USA file. Verified.
- A byte of 0x20 or more is one glyph, glyph = byte - 0x20 (`FUN_00191030`). Bytes 0x19 to 0x1f followed by a byte select glyph (byte - 0x19) * 0x100 + next + 0xe0. Every other byte below 0x20 is a command; its length is read from the table at 0x37ae50 (`FUN_00190f68` advances by it): 0 end (1 byte), 1 space (1), 2 newline (1), 3 reset colour and size (1), 4 colour from `ftst` (2), 7 colour RGBA (5), 9 icon (2), 0x0a size in pixels (2), 0x0b width in percent (2), 0x0c extra line gap (2), 0x0d variable (1), 0x10 end of text (1), 0x11 position (5), 0x13 (5), 0x14 (3), others per the table. Only 1, 2, 3, 7, 9, 0x0a, 0x0b, 0x0d, 0x08, 0x11, 0x13 and 0x14 occur in `sys.bar` (histogram of the file); 0x0c, 0x0e and 0x15 to 0x17 are parsed by the game but absent from it. Verified.
- Which glyph is which character was read off the atlas and checked against messages: digits 1 to 10, `+ - x`, A to Z from glyph 14, `! ? % /`, the period at glyph 47 (byte 0x4f), the apostrophe at 204, lower case from 122, the accented letters after `z`, buttons and arrows near 207 to 222. `text::glyph_char` maps them; glyphs it does not know print as `<gN>`. The older `kh2_tables::msg::decode` has several of these punctuation marks wrong (0x48 is `!`, 0x49 is `?`, 0x50 is `,`), which is not edited here.

### Layout (0x1a8210, 0x1a8698, 0x191108, 0x1a7f60)

- A message object holds a font, a size scale S and a width scale X. Size comes from the caller (command bars use 14) or command 0x0a: S = size / byte +0x11 of the descriptor (18 or 24). Width factor X = percent / 100 (command 0x0b). A glyph quad is `cell_w * S * X` wide and `cell_h * S` high with its bottom on the baseline. The advance is `(int)(width * S * X + 0.5)`; a space is `(descriptor +0x10) / 3` times the same factors.
- The first baseline is the line top plus the line height, the largest `byte +0x11 * S` on the line. A newline adds the descriptor's line gap (+0x14: 6 for the `sys` fonts, 2 for `evt`) and the extra gap of command 0x0c, then the next line's height. For font 1 at size 14 the line pitch is 20 pixels. Icons are 24x24 and span 20 pixels above the baseline to 4 below it; their advance is the icon width table. Two long dashes (glyph 0x46) in a row overlap: the second is glyph 0x47 drawn 2 pixels (scaled) to the left. Verified in code; rendered output checked by eye against the layout rules.
- Alignment of a block (0x1a8018, table 0x37b5e4): 0 left, 1 right, 2 centre, 3 centre both ways, 4 centre x and bottom, 5 bottom. Implemented per line.
- `Messages` and `layout` are pure; tests in `kh2-image/tests/disc.rs` read the disc (`KH2_ISO`) and skip without it.

### Colours

- Command 4 reads `ftst` of `03system.bin` (loaded at 0x193610 into 0x1a7dd8, looked up at 0x1a7df8): u32 version, u32 count (9), records of 0x50 bytes with a u32 id (1 to 8 and 10) and one RGBA word per world index 0 to 18. World index to code: zz, es, tt, di, hb, bb, he, al, mu, po, lk, lm, dc, wi, nm, wm, ca, tr, eh (table at 0x349dc0). Verified.

## Sora's panel (class built at 0x156520, per-frame at 0x157a50)

Verified in code unless marked.

- Objects (gaug sequence groups, decimal): circle 137 (danger 132), ring back 121 (danger 122), ring trail 121 then 126 after a hit, ring fill 128, bar back 124 (danger 125), bar trail 127, bar fill 129, cap 123, MP label 116, MP back 119, MP fill 115, MP cap 120. Table at 0x358970, init at 0x156108 and 0x1563c8, switching at 0x157230.
- Anchor of the panel is group 137's translation (455, 355). The ring layers are children of it; the MP bar objects are children of the MP label (anchor (-40, 31) when settled), so the MP bar's right end sits at (415, 386) and it grows to the left.
- HP value rule (0x155400, 0x155530, 0x1552a0, 0x155378): below 60 HP the value is a ring sweep of pi/40 per HP (constant at 0x379374), starting at the west end and running clockwise, 270 degrees at 60. At 60 and above the ring is full and a bar extends left from the ring's bottom, 3 pixels per HP over 60 (bar sprites are 100 pixels wide and scaled). The same rule is used for three values: maximum HP (back layer), the HP before the last hit (trail) and the current HP. The cap piece rotates by minus the maximum's sweep on the ring, and sits at the bar's far end rotated 90 degrees on the bar.
- Hit and heal (0x1574d8): on a change, the trail value becomes the previous HP when HP dropped and the new HP when it rose, and the trail groups (126 and 127) restart; they fade out by their own animation.
- Danger (0x1a0be0): HP at or below `max >> 2` switches circle, back layers and face to the red variants. The face groups are 3 (normal) and 0 (pulsing red). A hit shows the hurt face first; see "Sora's portrait (WP-FIX-8)".
- MP (0x157628): bar length is the maximum MP in pixels, fill is the current MP. While MP recharges the panel uses the recharge look, see below.
- The ring layers are clipped by "mask" objects (rectangles written to the GS depth buffer, 0x13e010, test registers 0x32001). The clip is implemented here as an exact wedge test; the shape follows from the ring's measured coverage (all but the south-west quadrant) and the cap's rotation. Inferred.

### Sora's portrait (WP-FIX-8)

**The blotches: palette order.** The user saw dark and blue speckle over Sora's hair, face and collar. Cause: the `face` IMGD of `obj/P_EX100.apdx` is a 256x128 PSMT8 image with its pixels in linear order (header flags 3, bit 2 clear) and a 16x16 PSMCT32 palette. The decoder applied the CSM1 palette order (pixel value bits 3 and 4 swapped) only to swizzled images, so this image read entries 8 to 15 where 16 to 23 belong (and so on in every 32), which scattered wrong colours over smooth areas. The game draws every IMGD through 0x233588: the CLUT is uploaded as the header's `+0x2c` x `+0x2e` rectangle (16 x 16) with buffer width `+0x30` and pixel mode `+0x32`, and TEX0 is built with CSM = 0 (bit 55 never set), i.e. CSM1, so the swap applies whatever the pixel layout; header flag bit 2 only changes how the pixels are uploaded (halved size as PSMCT32, same function). Fixed in `kh2_image::imgd::csm1_entry`. The same applies to the party faces (`P_EX020`, `P_EX030`, `P_AL000`, 48x48) and the `miss` image of the field file, all linear 8-bit. Other candidates were ruled out: the images are expanded to RGBA before any filtering (no filtering across palette indices), the face sprite rectangles are whole (one quad per group), and the blotches disappear with the palette order alone. Tests: `linear_eight_bit_palette_reads_in_csm1_order` (unit), `sora_face_palette_reads_in_csm1_order` (disc: the median colour step between opaque neighbours is 62 in CSM1 order against 116 in file order). Verified (before and after crops).

**The face's groups.** The face object (0x340 bytes; built by 0x153af0 from 0x156520 with the `face` pair of the member resource +0x7b0, 0x16b998) has four groups: 3 the normal face (loops), 1 the hurt face with gritted teeth (tinted red, fading to normal over frames 0 to 29, held to frame 59, plays once), 0 the tired face pulsing red (loops), 2 the eyes-closed face in red (loops). Group by panel state, 0x153dd0: state 0 -> 3, 1 -> 0, 2 -> 2.

**Panel state** (panel +0x18, written every frame by 0x157d40 from 0x157e48): 2 when the actor's flag +0x7f8 bit 4 is set (0x166710), else 1 when `hp <= max >> 2` (0x1666e8 -> 0x1a0be0), else 0. The circle, ring back and bar back groups by state are the table at 0x358970 (row `role * 3 + state`, read by 0x1558a0): circle 137 / 132 / 137, ring back 121 / 122 / 121, bar back 124 / 125 / 124. Bit 4 of +0x7f8 is set by 0x186580 (reached from 0x186568 and 0x1865a8) and cleared by 0x17cee8 (a revive path [inferred]: called from 0x186238 when a value rises while the bit is set); HP reaching 0 in 0x186238 calls 0x186530, which calls the actor's method +0x5c; that this leads to 0x186580 for Sora was not traced, so the port has no source for the knocked-out state and shows it only with `KH2_HUDKO=1`.

**The damage face (verified in code).** The party slot table at 0x355768 (three member pointers, then a bit word per slot) carries events to the panels: 0x13dd20, 0x13dd70, 0x13ddc0, 0x13de10 set bits 1 to 4 for the member's slot. The damage handler 0x175340 posts event 1 for an ordinary hit, event 2 when the hit's kind (byte +0x26 of the hit, through the jump table at 0x37abe0 in 0x18b700) is 3, event 3 when it is 4 or the member is knocked out; no event for attack types 5 and 6 (byte +4 of the attack data) or a kind-0 hit with no damage. 0x186238 posts event 4 when a value rises (a heal). The panel reads the bits at the start of its frame (0x157e48, after 0x157d40) and calls its methods (vtable 0x358a18, set by 0x32dba8): event 1 -> 0x1571d0, which is `0x157040(panel, 135)`; event 2 -> 0x1571e8 (134); event 3 -> 0x157200 (133); event 4 -> 0x157218 -> 0x157108. 0x157040: the HP trail (0x1574d8), the circle starts the given group with the state's circle as its follow-up (panel +0x1afc = circle object +0x17c), the ring and bar backs take the state's groups, and 0x153ee8(face, 1, state) starts face group 1 (the code passes 1 straight on as the group, disassembly at 0x153f08-0x153f14) and writes the state's face (0x153dd0) to the face object's +0x17c; it also starts the danger alarm (0x2c1528) when the state has just become 1. The object update 0x138aa8 steps the group; when a group with a non-zero play count has finished (player state not 1 or 2, 0x2369c0; a looping group, play count 0, 0x2369e0, never hands over) and +0x17c is not -1, it starts that group, clears +0x17c and steps once. So on every hit the hurt face plays once (60 frames, one second at the 60 Hz tick, which is inferred), then the face of the state the hit left (normal, or the danger face). The circle hit groups 135, 134, 133 flash red to black over 31, 46 and 61 frames with a horizontal shake of 4, 6 and 10 pixels and play once. A heal (0x157108) sets the trail values to the current HP, the circle (except on the first heal after the panel is built, flag +0x3b8b), the backs and the face to the state's groups at once and stops the alarm when danger ends. Without an event, a change of the danger state switches circle, backs and face (0x1572a0, 0x157310 -> 0x157230).

**Port** (`hud_gauge::panel_frame`, follow-up in `hud_gfx::HudScene::advance` / `set_group_then`). A drop of Sora's HP is treated as event 1 (circle 135, hurt face), a rise as event 4, otherwise a state change switches. Tests: `a_hit_shows_the_hurt_face_once_then_the_state_face`, `danger_without_a_hit_switches_the_face_directly`, `panel_state_follows_the_game_rule`. Harness: `KH2_HUDHP=7:15` (hit at 7 s: hurt face at 7.25 s, normal face from 8.0 s), `KH2_HUDHP=7:2` (hit into danger: hurt face, then the danger face), `KH2_HUDKO=1`. Not ported: hit kinds 2 and 3 (circles 134 and 133; the port does not know a hit's kind), heals of MP (the game posts event 4 for any rising value), the first-heal exception of +0x3b8b (when the game's first event 4 arrives was not traced; the port resets the circle on every heal). The danger alarm (0x2c1528 / 0x2c1550, bank 2 sound 9 through 0x2c14a8 / 0x2c14f0, `PlaySe::number(2009)`) is ported in WP-F1 (`hud_gauge::alarm_step`, docs/audio.md "The danger alarm"); its stop with a 0x3c-frame fade is logged only.

### MP recharge look (WP-4B2)

- `FUN_001a05d0` is true while the player's float at +0x1c0 is positive; +0x1bc is the progress and `FUN_001a05f0` returns `+0x1bc / +0x1c0`. When it turns true, 0x157628 switches the four MP objects from groups 116, 119, 115, 120 to 110, 113, 109, 114 (red art) and the label's follow-up from 117 to 111. The back bar is then drawn at scale 1.0 (100 pixels, `DAT_00379370`) with the cap 100 pixels left, and the fill scales by the progress ratio (0x1556a0, 0x1555f8). Verified in code; the pictures match (a magenta fill on a dark red bar).
- Input: resource `MpRecharge { progress, total }`; the player module fills it from its recharge state. `KH2_HUDMPRECHARGE=<progress>:<total>` forces it.

### Drive gauge (WP-4B2)

- Objects 12 to 15 of the panel (built at 0x155c78, per-frame 0x1577d0, mode switch 0x156868): all children of the HP circle's anchor; the digit, MAX tag, burst and fill are children of the bar. Groups by the player's mode byte at +0x1af (0 normal, 2 and 3 two form variants, 4 locked): bar intro 21 / 50 / 140 / 18 (0x155a30), bar idle 23 / 51 / 141 / 19 (0x155a88), fill 25 / 49 / 139 / 25 (0x155b08). The digit group is `table[points]` with the three tables at 0x3589c0 (groups 28 to 37), 0x3589e8 (54 to 63) and 0x358998 (144 to 153) selected by the mode (0x155978). The MAX tag is group 20, shown when `points >= max` (+0x1b1 and +0x1b2); a point gained plays group 22 (and sound 0x20 or 0x21, not ported). Verified: the objects, the groups, the tables; the picture lines up between the HP ring and the MP bar.
- The orange fill is shown through a rotating mask (object at +0x30f0 built by 0x13ded0: a 50x120 rectangle turned by `fraction * 0.004014` radians, 0x155738; in the form modes by `value * 23 / count` degrees, 0x1557f8). That mask geometry is not ported: the port reveals the fill sprite from its left edge by the fraction (0 to 99 of the next point). This is an approximation.
- Mode 3 (the summon timer) is fed: `summon.rs` puts the digit and the in-segment fill of 0x155bf0 into `DriveGauge` (`points`, `time_fill`; oracle-checked in `drive::tests::summon_gauge_matches_the_game`), and the fill sprite is revealed by that fraction. Not ported: the form-time fill of mode 2 (the drive form's timer through the same 0x155bf0; the port shows the digit and the bar only), the lock chains' attach and release animation, the burst sound. `FUN_00155f50` hides pieces by mode; the port shows the bar, fill and digit in every mode.
- Input: resource `DriveGauge { enabled, mode, points, max, fraction }`, off until the player has a drive gauge. `KH2_HUDDRIVE=<points>:<max>:<fraction>[:mode]` (mode 0, 2, 3, 4) forces it.

## Target gauge (class at 0x1540a0, update 0x154498, hit 0x154758, bind 0x19b4a8)

- Anchor (498, 31) from group 38 ("HP" tag). One 200-pixel segment per 200 HP: back bar (group 39), cap (40), trail (41, flashes then fades after a hit), current (43), frame (42, 205 pixels wide: its four quads span x 296 to 501 around the anchor). Bar widths in pixels equal the HP inside the segment; the segment arithmetic (C truncating division) is ported from 0x154498. Verified.
- Frame rule (WP-FIX-12; 0x154498, +0x3b19; hide is 0x139800 which sets flag 0x40 of the object, show is 0x139810). Every frame 0x139bb0(6) shows all objects of the gauge's draw tag, then 0x154498 sets +0x3b19 to 1 only when the current HP's segment index (`(hp - 1) / 200`, 0x154458) equals the top segment index (`(max - 1) / 200`) and is not 0, and hides the frame object at +0x1bc otherwise. So an enemy of 200 HP or less never has the frame, and a bigger one has it only while its HP is in the top segment. The earlier port showed the frame always; its dark interior made every gauge look 200 HP long ("ghosting": the user's report 2026-10-06), a Shadow whose segment was 10 HP (current 8) looked like a nearly full bar with a bright block at the end. Fixed in `hud_target.rs` (`frame_shown`); the bar, cap, trail and current layers were already right (0x154328 scales and moves nodes 2, 4 and 5, and the cap, node 3, follows node 2). The trail layer (41) fades out by its own animation and draws nothing from frame 100 on (checked in the node dump). Verified in code and by screenshot (the same fight: back bar 10 pixels, current 8, no frame).
- Pip row (WP-4B2; 0x1540a0, 0x153ff8, 0x1543f0, 0x154758): up to 16 pairs of objects, children of the tag, laid out to the left with each pair a further `unk20` of group 45 (see the group record above). Group 45 is the pip's back and is shown for every segment below the top one, `(max - 1) / 200` of them. Group 44 is a filled pip, shown for each full segment left under the current one; a pip that was lost on the last hit (up to the previous HP's segments) switches to group 46. Verified in code; checked with 650 of 900 HP (three filled pips on four backs).
- The gauge is bound to the player's target when a status flag is set (status +0x1cc bit 0x80000, set at 0x14dfe8); which enemies get it and when it goes away were not resolved. This port shows it for the lock-on target and for 5 seconds after an enemy loses HP. Inferred stand-in.
- `KH2_HUDTARGETTEST=<hp>:<max>` draws the gauge for those values without an enemy.

## Lock-on reticle

- Pool of field icons: 0x13e5a0 (nine slots), created by 0x13e528 with a group number (0x13e1f0: the icon is the group, and a second member of group 20 is its speech bubble, hidden at creation), placed at a projected world point (0x13e968). The controller is 0x11a9b0: the icon group is 25 once a target is acquired and 3 otherwise; with no target the point is the camera position plus the camera's forward vector times a distance (0x11a5f8, the constant at 0x3788f8 is 300 units). The icon is hidden only while an event is running (`FUN_00196418` is `DAT_0035e3a4 != 0`, the event object). So the free-aim reticle is on screen whenever nothing is locked. Verified in code; the reading that group 3 is the yellow bracket is from the picture.

## Command menu (WP-4B2)

Module `hud_menu.rs`; art `comw` from the command file; group tables read from the executable at run time (`Tables::from_exe`).

Verified in code.

## Screen-edge layout (WP-FIX-12, the user's request)

The original lays the HUD out on its 512x448 screen. The port draws that box fitted by height (`ScalingMode::AutoMin`), so a 16:9 window used to show the whole HUD inside a 4:3 box in the middle: the command deck a quarter in from the left and the HP ring and MP bar three quarters across. The user asked for the command deck at the left edge and the HP ring and MP bar at the right edge, which is also what the reference clips show (`local/VIDEOS.md`, 4.mp4 and 9.mp4).

- Rule: every root node has an `Edge` (`hud_gfx.rs`): `Left`, `Right` or `Center`. The window's extra width (`side_margin`: `(width / scale - 512) / 2` HUD units, 142.2 at 16:9, 42.7 at 4:3: the HUD box is 8:7, so only a window at 8:7 or narrower has none) is added to the root's x: minus for `Left`, plus for `Right`; children follow their parent. The distance from the screen edge is therefore the 4:3 layout's own margin (the command bars start 28 units from the left edge, the ring's anchor (455, 355) is 57 units from the right edge).
- Left: the command menu (headers, bars, plates, icons, arrows, the reaction capsule; `hud_menu.rs`). Right: Sora's panel (circle, rings, bars, cap, face, MP bar, drive gauge: `hud_gauge.rs`) and the party panels (`hud_party.rs`). Centre: the target gauge (top right, anchor (498, 31), left as it was because it is not in the user's list; moving it is one line, `Edge::Right` on the tag in `hud_target.rs build`), the lock-on reticle (projected from the world), banners, the area card, message windows, number strips.
- Executable: no 16:9 or safe-area parameter was found. The HUD objects take their position from the sequence anchors and constants in the menu and panel code; none reads an aspect value (searched: the panel build 0x156520 and the menu code 0x13c4b0 and 0x13bc50 read only the group tables and file names as data). Gap: the draw environment setup (the 0x7000 and 0x7300 vertex constants) was not traced to its source, so a global screen-mode flag is not ruled out. The PS2 game draws a 4:3 frame; the edge anchoring is an addition for the user's widescreen window, not an original rule.
- `KH2_HUD_43=1` keeps the original layout (the HUD in the 4:3 box). The log line `hud: edge layout, ... (N HUD units of margin per side)` or `hud: 4:3 layout (no side margin)` is printed when the margin changes (once at start; again on a window resize).
- Tests: `hud_gfx::tests::side_margin_splits_the_extra_width`, `edge_anchored_roots_move_to_the_screen_edges`.

## Rendering notes

A second camera (order 10, render layer 7, same MSAA setting as the 3D camera; a different setting smeared the previous frames) shows the 512x448 HUD scaled to fit the window; wider windows get empty margins. Quads become triangles with vertex colours, one mesh per run of equal texture, blend and filter, rebuilt every frame. Colours are modulated in linear light with the vertex colour raised to 2.2 so opaque colours match the PS2's gamma-space product; the alpha blend itself happens in linear light, so translucent edges differ slightly from the original. Text uses the same path: the font atlases and the icon atlas become textures (one per palette row), glyph quads are ordinary quads.

## Phase 3 (WP-4B3)

**Reaction capsule hook** (docs/limits-reactions.md hook 1). `hud_menu` is `pub(crate)` and `hud_menu::mirror_reaction` copies `ReactionOffer` into `CommandMenu.reaction` every frame while the offer's status is Available (`alt` from the command's Flags bit 3; the entry-type-7 variant has no source). The menu is now visible in play with the four basic commands (Execute 1 to 4) and the cursor on the first, since the player's command lists (+0x974, 0x13ca30) have no source in the port; this is a stand-in list. Run with `KH2_REACTION_FAKE=457`: the capsule shows message 48047 ("D-Charge") above the list.

**Text commands** (`kh2_image::text`, from 0x1a8210, 0x1a8978, 0x1a8b48, 0x191108). Verified in code:
- 0x11 sets the pen to (x, y) from the message origin as two i16; the new baseline is `y - line height` and no line gap is added (case 0x11 stores `origin + y*16 - lineheight*16`). Layout keeps what was drawn before it and continues on the new baseline.
- 0x0e stores `byte << 3` (1/16 pixel units, so half a pixel per unit) as the skew; only font mode 4 uses it (0x1a8ee0 passes it to 0x1a9818, which moves the top edge right and the bottom edge left by it, the quad vertices at 0x1a9818). Mode 4 is drawn with its own shaded palette row; shadows and outlines are drawn unskewed.
- Typewriter: every draw of a message (0x1a80d8) raises a counter (+0x1c) by one, the layout starts with it and tests it before each token (`< 0` ends the text, 0x1a8210 top of loop); each glyph and icon lowers it by the message's cost (command 0x17 byte 1, read when the message object is built, 0x1a8978: +0x5c), command 0x14 lowers it by its u16 value, and glyphs whose counter/fade is below 1 are drawn with alpha `counter / fade` (0x1a8698; fade is command 0x17 byte 2, +0x4c). The port counts one per 60 Hz HUD tick per visible label (`Node::label_time`). Without 0x17 nothing is cut.
- 0x15 and 0x16 advance the pen 32 pixels (0x200 GS units) and call the owner (a slot callback with the index, and a button callback); 0x191108 measures the same 32 pixels. The port advances and draws nothing there (the owning window draws the icon).
- 0x05, 0x06, 0x08, 0x0f, 0x12 and 0x13 are owner callbacks or events with no layout effect (0x1a8b48 scans the page for 0x05 when it ends; 0x13 stores two u16 into the owner; 0x12 calls 0x197b70, an event dispatcher). Kept as `Token::Callback`. The real `sys.bar` holds 5 position commands, 1 wait and 2 callbacks of 0x08 or 0x13 (test `phase_three_commands_in_real_messages`).
- The shadow alpha is now taken from the message's base colour alpha once (0x1a8de0 sets the shadow colour, 0x1a80d8 applies it), not per glyph.

**Message windows (dialogue).** The window object is the vtable at 0x35eac0 (constructed by 0x1ab830 and 0x1ab8e0 over the base 0x1aaf20; draw 0x1ab370, state machine 0x1ab170): states 0 opening (a sequence player), 1 waiting for the message to be ready, 2 running (the text object is drawn, the paging cursor or button prompt is placed by 0x1aa4e8 and 0x1aa6b8), 4 to 7 closing. The frame is a sequence player with groups chosen from the string at 0x35ea48 by the window type; the text is drawn by 0x1a80d8 inside it and the page ends are the end-of-text (0x10) and 0x02/0x05 handling above. The frame art was found in WP-6D; see "Message windows (WP-6D)" below.

**Area-name card** (`hud_card.rs`). Found. 0x149bb8 (area start) calls 0x15ade8 unless the world/area bytes are unchanged (0x105070 compares 0x33e830 with 0x33e848) or 0x1b9550 is set. 0x15ade8 calls 0x19e178, which indexes the place table (`msg/us/place.bin`, path 0x37b3f0, loaded by 0x19e088) through 0x19e0c8 (a BAR entry of type 2 keyed by the world code, 4 bytes per area: a u16 message id and a u16 offset) and looks the id up in the message tables (0x190c40: `sys.bar`, then the world's `msg/us/<world>.bar` that 0x190dd0 names, then `jm` or `gumi` for the special worlds). The text goes to the card object (0x358ba8, vtable 0x358bb8) through 0x15a5e0 with a timer of 120 (0x379420) and the card draws it for that many frames (update 0x15a640 counts 1.0 per frame while no event is running, `FUN_00196418`) with 0x1a8d18: font 2, x 256, y 192, colour 0x80ffffff, alignment 4 (centred, bottom at y). A picture variant (0x15a6f0, object 0x358ba4) is used when the world object provides an image and sequence (`FUN_00149210` and `FUN_00149218`); that path is not in the decompiled set and not ported. The earlier note that `place.bin` is a Shift-JIS table was wrong: it is a BAR of message ids and the names are the USA messages (area `tt00` gives "The Empty Realm" in this port, read from the disc). Run `KH2_HUDCARD=1` to keep it up, `KH2_HUDCARD=<world>:<n>` to show another place. Note the mapping from the port's area name (`tt00`, parsed as world `tt`, area 0) to the game's area index is the obvious one but not verified against the 0x33e830/0x33e848 bytes.

**Number strips** (`hud_banner::update_strips`). 0x151970 and 0x151d48 build objects of the `fiel` pair: a strip (group 17 or 48) and six digit players; 0x1518c8 and 0x151ca0 format the value with `%d` (0x379430, 0x15b010) and give digit k the group `table[digit]` (tables 0x3586e8: groups 28 to 37, and 0x358730: groups 38 to 47), advancing by each group's `unk20`. They are raised by 0x1a39b0 (the per-level routine, through 0x14f2d8) and by 0x15b198 (through 0x14f2b8). Which of them is "the level-up screen" was inferred from the call sites, the digits' placement beside the strip is inferred, and in the harness run (`KH2_HUDSTRIP=levelup:127`) nothing was visible on screen, so this part is unverified: treat it as ported data and layout but not as a checked picture.

**Party panels** (`hud_party.rs`). Built as 0x154a78 does (circle 71, rings 64 (trail), 65 (HP), 66 (MP), the member's `face`, five mask objects of 0x13e010; two panels allocated by 0x13d738, the second `unk20` of group 71 below the first). The trail value's update for party members was not read (Sora's rule is reused, inferred).
- UV scrolling inside a sprite rectangle (no scrolling sprites in these files; the player wraps without the GS region clamp).
- Whether the 3D view itself is a 512x416 region (the projection offset suggests it).

## Message windows (WP-6D)

Module `hud_msgwin.rs`; rules in `kh2_image::window` and `Seqd::resize_frame`. Verified in code unless marked.

**Files.** The frame is a sequence: `msg/us/fontinfo.bar`, entry `md_m` (type 25), loaded by 0x1a8ff8 into 0x1c958b0 (returned by 0x1a9dc8). Its texture is the window texture object 0x1c95710 (returned by 0x1a9db8, set up empty by 0x1a9e40): 0x190b70, which binds a message file as table `n`, uploads the file's `md_m` IMGD (type 24) into it through 0x1a9368 when the entry is not empty. The world's message file `msg/us/<world>.bar` is bound as table 2 when an area loads (0x168ba8 calls 0x190e70 with the world byte 0x33e830); the system file `sys.bar` and the special files `jm.bar` and `gumi.bar` carry an empty `md_m`. The world files sit in the world sub-indexes (`000tt.idx`); each holds a 256x128 8-bit image, and the images differ from world to world (tt, hb, eh, al compared). Checked by `window_frames_in_the_font_and_world_files` in `kh2-image/tests/disc.rs`.

**Frame kinds and groups.** The base window 0x1aaf20 takes a frame kind 0 to 9 (its eighth argument, stored at +0x1d0) and plays groups from the string at 0x35ea48, three characters per kind: `kind*3` opening (state 0), `+1` idle (state 1 on, 0x1ab170), `+2` closing (state 5 to 6). The characters are "CDEF..." so kind `k` uses groups 67 + 3k, 68 + 3k, 69 + 3k. In the file the opening and closing groups play once (loops 1) and the idle group loops; each draws one nine-part sprite group (kind 0: 16x16 corners at texels (0,0)-(32,48), the orange rounded frame; kind 4: texels (51,97)-(81,127), the black frame). The opening animation of kind 0 is a black copy at alpha 0x10 to 0x20 sliding to (3, 3) under the frame fading in from alpha 0x40, a drop shadow [inferred from the colours and offsets].

**Frame sizing (0x2387c0).** Every draw (0x1ab370) first rewrites the nine parts of the current group's first animation's sprite group in the shared sequence data: the box is the text size plus the group record's `x` and `y` (margins: kind 0 16 and 8, kind 1 10 and 8, kind 2 16 and 8, kind 3 8 and 8, kinds 4 to 9 none), full size rounded down to even; corners keep their size outside the box, edges are stretched along it, the centre fills it, all centred on the frame's draw point. Test `frames_stretch_around_the_box` and the disc test check the part rectangles.

**Text box.** The window measures its message (0x191570: every page up to an end-of-text 0x10, widest line and sum of line heights plus gaps, the largest page, each side rounded up to even) and keeps the size at +0x5c and +0x60 (text object +0x50, +0x54). The text is drawn by 0x1aac80 through 0x1a80d8 at the window's x, y with the text object's alignment (+0x64, 3 = centred both ways, set by the base constructor 0x1aa928) and the colour of `ftst` id given to the constructor, looked up for the current world (0x1a7df8).

**Classes.** Constructors with their values (font, colour id, x, y, frame kind):
- 0x1ab6a8 (vtable 0x35eb80): font 3, colour 5, (128, 104), kind 0. Opened by the event message code 0x2275a8 for message kind 0, by 0x172360 and by 0x2c5cf0 (which moves it to (256, 48) with alignment 2).
