It is the survey's "next kinds" row 12: al01, bb08, he09, mu02, nm02, nm06. In al01, bb08, mu02 and nm06 a spawn tag (b_70; bb08 and nm06 also b_71) holds two group records: a kind-1 record of decoys (bb08 0x545, mu02 0x2a5, al01 0x1b9, nm06 0x3fe and 0x41f; spawn kind 1, spawn word +0x20 = 1, so host 1.39 `spawn_param(1)` is 1) and a kind-2 record with the fighting members (bb08 0x565, mu02 0x2c5, al01 0x1d9, nm06 0x41e and 0x43f; spawn kind 2, +0x20 = 0) whose header flag byte (+1) has bit 0 set, so it starts disabled (`FUN_00198430`). he09 b_9n is a plain kind-2 record (flags 0, wave byte 100) of three `M_EX590`; nm02 b_70's record 0x35b is disabled like the others and holds one.

What enables the fighting group (WP-EN15b). The disabled record carries one signal (8 bytes after the walk paths: `u16 event, u16 arg, u8 action`) = (0x9b, its own id, 0). `FUN_00198430` registers the group with the trigger table when it is set up (`FUN_001975e0` finds or makes the record of `(event, arg)` in the 0x80-slot table at `DAT_01c8a9c8`; `FUN_00197838` adds the group id with action 0), and a raised event 0x9b runs `FUN_001978b0`, which calls `FUN_00199c70(id)` (clears bit 0 of the group object's +4, found by `FUN_00199bf8`) and frees the record. `FUN_00197b70(event, arg)` -> `FUN_00197670` -> `FUN_00197588` picks the record: the exact `(event, arg)`; else, when the raised argument or the record's is negative, the last matching slot of the scan; `FUN_001975e0` takes the highest free slot, so that is the record made first [inferred from its loop, which keeps the last free slot it passes].
Nothing in area data raises 0x9b: no kind-3 or kind-4 group has +0x1c = 0x9b (`FUN_00199930` and `FUN_00199b18` send +0x1c with the group's id or the object's), no area-script trigger (opcode 0xc) of bb08, mu02, al01 or nm06 uses it, and the `FUN_00197b70` callers with a literal send the story, exit and battle-result events (1, 2, 3, 4, 0xf, 0x11, 0x15, 0x1f, 0x21, 0x22, 0x24, 0x4b, 0x4c, 0x50, 0x51, 0x5a, 0x87, 0x8c, 0x97, 0x9d, 0x9e). The sender is a BDX script call: host 1.41 is `FUN_001727b0(args)` = `FUN_00197b70(args[0], args[1])` (its entry is the word after 0x35bef0 in the group-1 table at 0x35bda8, entry 41, `{function, flags}` with 2 arguments; `names.rs` has no name for it). A scan of every script (`kh2 bdx --scan` with a counter on host 1.41 preceded by a push of 155; the counter was not committed) finds eight: the field objects `F_AL050`, `F_BB040`, `F_BB070`, `F_HE000`, `F_MU040`, `F_MU050`, `F_MU060`, `F_NM070` (props in Agrabah, Beast's Castle, the Coliseum, Land of Dragons and Halloween Town; by model name only). In `F_BB070` (`cargo run -p kh2 -- bdx F_BB070`) the handler of the damage event 6 (entry 0x0016) runs the hit reaction (2.64) and, for reactions 6 to 11, routine R0061: when progress flag 0x102b (host 0.70) is set and the word at +0x90 of its globals is non-zero it pushes 155 and -1 (0x006d, 0x0070), calls host 1.41 (0x0073) and sends itself `break` (1.90). So breaking such a prop raises event 0x9b with argument -1 and opens the first-registered group that waits for 0x9b: the props hide the Heartless. The app has no field objects (`F_*` models are not loaded), so in play the event does not come by itself.

App (`enemy.rs`). `GroupSignal` / `area_signals` read the signals of the area file; `TriggerTable` is the table (`register`, `fire` with the rule above); `BattleGroups::triggers` and `BattleGroups::off` (ids of disabled groups) are filled when the groups are set up; the per-tick walk skips a group in `off` (`FUN_001989d8` does nothing for a disabled group, its timer included); the system `fire_group_triggers` (after `spawn_waves`) applies the global events (`struggle::GlobalEvent`) to the table: action 0 enables, 1 disables, and the group's `PartCount` follows. A disabled kind-2 group is set up like the others now (it was dropped before). No other area the app reaches changes: the disc scan finds signals with event 0x9b in seven records only (al01, bb08 twice, he07, mu02, nm06 twice) and none in tt00, tt02, tt04. Harness: `KH2_FIRE_EVENT=<hex event>[,<argument>]` raises one event once after the groups are set up (argument -1 when omitted; it goes to the table only, the objects' event 10 is not sent). Host 1.320 (`FUN_00199580`, the sum of the groups' enemy counters) answers the sum of `PartCount::count` now (`enemy_host::set_group_enemy_sum`, set by `fire_group_triggers` each tick), which R0ee1 reads for its speed scaling (1/1800 when positive, 1/600 at 0): it was 0, which drained the clock below three times too fast.

What it does. The script's init sets the general damage multiplier to 0: the call at 0x07f3 is host 1.311 `set_scaled_byte(status, 6, 0)` (`FUN_001a0ba0`: byte 6 of the status block's damage scales = (halfword 6 of the status template x 0 + 99) / 100 = 0, after host 2.9 built the block at 0x07b6), and the hit rule `FUN_0018b618` (element multiplier x general multiplier == 0) makes every hit ineffective. So it can be hit (the spark of an ineffective hit, flinch, `ineffective true`, the damage popup shows 0) but loses no HP to Sora, and the player cannot kill it. Its own HP (200 from `enmp` row 4) is a clock: R0ee1 lowers it by (a speed) / 1800 (or / 600) per frame time through host 1.155 `obj_method_78` while it moves, and at HP 1 the script enters `gacha_leave` and then `leave`; the object hides and is retired (host 1.328, which sets +0x7f8 bit 4: `FUN_001993f8` keeps a member of a wave up to 99 in the defeated table, so it does not come back; wave 100 comes back).
