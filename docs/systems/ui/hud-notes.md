## Screen-edge layout (WP-FIX-12, the user's request)

The original lays the HUD out on its 512x448 screen. The port draws that box fitted by height (`ScalingMode::AutoMin`), so a 16:9 window used to show the whole HUD inside a 4:3 box in the middle: the command deck a quarter in from the left and the HP ring and MP bar three quarters across. The user asked for the command deck at the left edge and the HP ring and MP bar at the right edge, which is also what the reference clips show (`agents/RECIPES.md` R6, 4.mp4 and 9.mp4).

- Rule: every root node has an `Edge` (`hud_gfx.rs`): `Left`, `Right` or `Center`. The window's extra width (`side_margin`: `(width / scale - 512) / 2` HUD units, 142.2 at 16:9, 42.7 at 4:3: the HUD box is 8:7, so only a window at 8:7 or narrower has none) is added to the root's x: minus for `Left`, plus for `Right`; children follow their parent. The distance from the screen edge is therefore the 4:3 layout's own margin (the command bars start 28 units from the left edge, the ring's anchor (455, 355) is 57 units from the right edge).
- Left: the command menu (headers, bars, plates, icons, arrows, the reaction capsule; `hud_menu.rs`). Right: Sora's panel (circle, rings, bars, cap, face, MP bar, drive gauge: `hud_gauge.rs`) and the party panels (`hud_party.rs`). Centre: the target gauge (top right, anchor (498, 31), left as it was because it is not in the user's list; moving it is one line, `Edge::Right` on the tag in `hud_target.rs build`), the lock-on reticle (projected from the world), banners, the area card, message windows, number strips.
- Executable: no 16:9 or safe-area parameter was found. The HUD objects take their position from the sequence anchors and constants in the menu and panel code; none reads an aspect value (searched: the panel build 0x156520 and the menu code 0x13c4b0 and 0x13bc50 read only the group tables and file names as data). Gap: the draw environment setup (the 0x7000 and 0x7300 vertex constants) was not traced to its source, so a global screen-mode flag is not ruled out. The PS2 game draws a 4:3 frame; the edge anchoring is an addition for the user's widescreen window, not an original rule.
- `KH2_HUD_43=1` keeps the original layout (the HUD in the 4:3 box). The log line `hud: edge layout, ... (N HUD units of margin per side)` or `hud: 4:3 layout (no side margin)` is printed when the margin changes (once at start; again on a window resize).
- Tests: `hud_gfx::tests::side_margin_splits_the_extra_width`, `edge_anchored_roots_move_to_the_screen_edges`.

## Debug aids

`KH2_HUD_43=1`: the original 4:3 layout in the middle of a wide window (see "Screen-edge layout"). `KH2_HUDFREEZE=<frame>` holds the lock-on reticle's group at that frame. `KH2_DEBUGHUD=1` or F9: developer text and damage text. `KH2_HUDLOG=<seconds>`: dump every HUD node and draw batch once. `KH2_HUDHIDE=3,9`: hide nodes by index. `KH2_HUDTEST=hp,max,mp,mpmax`: draw other values than the game state holds (display only). Phase 2: `KH2_HUDTEXT=<hex id>[:font[:size[:x:y]]]` (comma separated), `KH2_HUDMENU`, `KH2_HUDDRIVE`, `KH2_HUDMPRECHARGE`, `KH2_HUDTARGETTEST`, `KH2_HUDBUBBLE`, `KH2_HUDBANNER`, `KH2_HUDEXP`, `KH2_HUDFREEZE` as described above. WP-FIX-8: `KH2_HUDHP=<s>:<hp>,...` (the panel shows that HP from each time on: hits, danger, heals at known times; display only), `KH2_HUDKO=1` (knocked-out state); every face change logs `hud: portrait face group N`.

## Rendering notes

A second camera (order 10, render layer 7, same MSAA setting as the 3D camera; a different setting smeared the previous frames) shows the 512x448 HUD scaled to fit the window; wider windows get empty margins. Quads become triangles with vertex colours, one mesh per run of equal texture, blend and filter, rebuilt every frame. Colours are modulated in linear light with the vertex colour raised to 2.2 so opaque colours match the PS2's gamma-space product; the alpha blend itself happens in linear light, so translucent edges differ slightly from the original. Text uses the same path: the font atlases and the icon atlas become textures (one per palette row), glyph quads are ordinary quads.

## Phase 3 (WP-4B3)

**Reaction capsule hook** (docs/systems/drive-limits-summons/contract.md hook 1). `hud_menu` is `pub(crate)` and `hud_menu::mirror_reaction` copies `ReactionOffer` into `CommandMenu.reaction` every frame while the offer's status is Available (`alt` from the command's Flags bit 3; the entry-type-7 variant has no source). The menu is now visible in play with the four basic commands (Execute 1 to 4) and the cursor on the first, since the player's command lists (+0x974, 0x13ca30) have no source in the port; this is a stand-in list. Run with `KH2_REACTION_FAKE=457`: the capsule shows message 48047 ("D-Charge") above the list.

**Text commands** (`kh2_image::text`, from 0x1a8210, 0x1a8978, 0x1a8b48, 0x191108). Verified in code:
- 0x11 sets the pen to (x, y) from the message origin as two i16; the new baseline is `y - line height` and no line gap is added (case 0x11 stores `origin + y*16 - lineheight*16`). Layout keeps what was drawn before it and continues on the new baseline.
- 0x0e stores `byte << 3` (1/16 pixel units, so half a pixel per unit) as the skew; only font mode 4 uses it (0x1a8ee0 passes it to 0x1a9818, which moves the top edge right and the bottom edge left by it, the quad vertices at 0x1a9818). Mode 4 is drawn with its own shaded palette row; shadows and outlines are drawn unskewed.
- Typewriter: every draw of a message (0x1a80d8) raises a counter (+0x1c) by one, the layout starts with it and tests it before each token (`< 0` ends the text, 0x1a8210 top of loop); each glyph and icon lowers it by the message's cost (command 0x17 byte 1, read when the message object is built, 0x1a8978: +0x5c), command 0x14 lowers it by its u16 value, and glyphs whose counter/fade is below 1 are drawn with alpha `counter / fade` (0x1a8698; fade is command 0x17 byte 2, +0x4c). The port counts one per 60 Hz HUD tick per visible label (`Node::label_time`). Without 0x17 nothing is cut.
- 0x15 and 0x16 advance the pen 32 pixels (0x200 GS units) and call the owner (a slot callback with the index, and a button callback); 0x191108 measures the same 32 pixels. The port advances and draws nothing there (the owning window draws the icon).
- 0x05, 0x06, 0x08, 0x0f, 0x12 and 0x13 are owner callbacks or events with no layout effect (0x1a8b48 scans the page for 0x05 when it ends; 0x13 stores two u16 into the owner; 0x12 calls 0x197b70, an event dispatcher). Kept as `Token::Callback`. The real `sys.bar` holds 5 position commands, 1 wait and 2 callbacks of 0x08 or 0x13 (test `phase_three_commands_in_real_messages`).
- The shadow alpha is now taken from the message's base colour alpha once (0x1a8de0 sets the shadow colour, 0x1a80d8 applies it), not per glyph.

**Message windows (dialogue).** The window object is the vtable at 0x35eac0 (constructed by 0x1ab830 and 0x1ab8e0 over the base 0x1aaf20; draw 0x1ab370, state machine 0x1ab170): states 0 opening (a sequence player), 1 waiting for the message to be ready, 2 running (the text object is drawn, the paging cursor or button prompt is placed by 0x1aa4e8 and 0x1aa6b8), 4 to 7 closing. The frame is a sequence player with groups chosen from the string at 0x35ea48 by the window type; the text is drawn by 0x1a80d8 inside it and the page ends are the end-of-text (0x10) and 0x02/0x05 handling above. The frame art was found in WP-6D; see "Message windows (WP-6D)" below.

**Area-name card** (`hud_card.rs`). Found. 0x149bb8 (area start) calls 0x15ade8 unless the world/area bytes are unchanged (0x105070 compares 0x33e830 with 0x33e848) or 0x1b9550 is set. 0x15ade8 calls 0x19e178, which indexes the place table (`msg/us/place.bin`, path 0x37b3f0, loaded by 0x19e088) through 0x19e0c8 (a BAR entry of type 2 keyed by the world code, 4 bytes per area: a u16 message id and a u16 offset) and looks the id up in the message tables (0x190c40: `sys.bar`, then the world's `msg/us/<world>.bar` that 0x190dd0 names, then `jm` or `gumi` for the special worlds). The text goes to the card object (0x358ba8, vtable 0x358bb8) through 0x15a5e0 with a timer of 120 (0x379420) and the card draws it for that many frames (update 0x15a640 counts 1.0 per frame while no event is running, `FUN_00196418`) with 0x1a8d18: font 2, x 256, y 192, colour 0x80ffffff, alignment 4 (centred, bottom at y). A picture variant (0x15a6f0, object 0x358ba4) is used when the world object provides an image and sequence (`FUN_00149210` and `FUN_00149218`); that path is not in the decompiled set and not ported. The earlier note that `place.bin` is a Shift-JIS table was wrong: it is a BAR of message ids and the names are the USA messages (area `tt00` gives "The Empty Realm" in this port, read from the disc). Run `KH2_HUDCARD=1` to keep it up, `KH2_HUDCARD=<world>:<n>` to show another place. Note the mapping from the port's area name (`tt00`, parsed as world `tt`, area 0) to the game's area index is the obvious one but not verified against the 0x33e830/0x33e848 bytes.

**Number strips** (`hud_banner::update_strips`). 0x151970 and 0x151d48 build objects of the `fiel` pair: a strip (group 17 or 48) and six digit players; 0x1518c8 and 0x151ca0 format the value with `%d` (0x379430, 0x15b010) and give digit k the group `table[digit]` (tables 0x3586e8: groups 28 to 37, and 0x358730: groups 38 to 47), advancing by each group's `unk20`. They are raised by 0x1a39b0 (the per-level routine, through 0x14f2d8) and by 0x15b198 (through 0x14f2b8). Which of them is "the level-up screen" was inferred from the call sites, the digits' placement beside the strip is inferred, and in the harness run (`KH2_HUDSTRIP=levelup:127`) nothing was visible on screen, so this part is unverified: treat it as ported data and layout but not as a checked picture.

**Party panels** (`hud_party.rs`). Built as 0x154a78 does (circle 71, rings 64 (trail), 65 (HP), 66 (MP), the member's `face`, five mask objects of 0x13e010; two panels allocated by 0x13d738, the second `unk20` of group 71 below the first). The masks: 0x13e010 builds depth-only rectangles (TEST 0x32001): a 64x64 square at (-32, -32) from the ring centre turned by an angle (0x13ea18 and 0x13e968 project its four corners), plus a second rectangle. Rules read in 0x154818 (HP, angle `f*pi - pi/2`; second rectangle the north-west quadrant while f < 0.5) and 0x154930 (MP, angle `(1 - f)*pi`; second rectangle the north-east quadrant while f < 0.5), with f = value / maximum (0x166730). Reading those as hiding masks gives a visible HP arc growing from south clockwise through west by 180 degrees x f and an MP arc from south counter-clockwise through east, which is what `hp_wedge` and `mp_wedge` compute (`HudScene` nodes gained `sweep_start`). The reading of the mask geometry is an inference from the setup values; a real picture of the original (WP-UI1, 2026-10-12: Goofy above Donald on the right edge, green HP arc on the left half and blue MP arc on the right half of each ring, ring about 0.47 of Sora's ring wide, 0.24 of it to the right of his centre and 0.77 above it) matches the port's geometry in the harness (`KH2_HUDPARTY=60:60:80:100;40:60:30:100`). The faces (WP-UI1): each panel shows its member's own `face` pair (group 3), loaded from `obj/<model>.apdx` (Donald `P_EX020`, Goofy `P_EX030`) by `hud_party::update` from the members in the field (slot 0 Donald, nearest Sora; slot 1 Goofy above him); before WP-UI1 the rings were empty because nothing loaded a face. Data path: `PartyMembers` (empty: draws nothing); `KH2_HUDPARTY=<hp>:<max>:<mp>:<max>[;...]` fills it for a look. The panel position relative to the screen comes from the circle group's own anchor plus `unk20` per slot; the rings in the harness screenshot appeared at the right edge above Sora's panel, which is consistent with that but not checked against the game. The trail value's update for party members was not read (Sora's rule is reused, inferred).
