## 13. M3 as built, part 1: the Items pages (WP-M3)

Code: `menu_items.rs`, a child module of `menu` (`#[path] pub mod item_pages;`; its plugin is added by `MenuPlugin`, so `main.rs` is untouched), `progress.rs` (`apply_boost`, `boost_maxed`), `kh2-image/tests/menu_items.rs` (disc tests that print the tables and group boxes). Page 0's confirm on the Items row (entry 0) opens page 1 (the module takes the key before `menu::input`, as the Abilities pages do).

**Pages and what a key does [V from the page handlers, addresses below].**
- **Page 1** (`FUN_0025ae18`): one row per party member, then the Stock row (message 0x455). Confirm on Stock opens page 0xa (the stock list is built with filter 0, `FUN_0025e790(0)`); confirm on a member opens page 2, his categories (`FUN_00269580`, stage M4, section 15); cancel (-2) goes to page 0, -4 closes, -5 would switch to Abilities (not ported, no entry point in `menu_abilities`). The help line is message 0x3b86 on a member and 0x3b87 on Stock (`FUN_0025ddc0`: 0xbb86 / 0xbb87).
- **Page 0xa**, the Stock (`FUN_0025b6e0`, built by `FUN_0025b2a0`): a grid of two columns and nine rows (`FUN_00298e40(list, 2, 9)`). The entries come from `FUN_00283a70(list, 0, arg)` and the sort `FUN_002845a0`: every item row, in table order, whose type is in the filter word (`FUN_00283810`), of which the player owns at least one (`FUN_001a1cc8`), and that no set story flag hides (`FUN_002846f0`, pairs at 0x382450: three items under flag 0x4d; the app has no such flag, so nothing is hidden). Entries are 6 bytes: id, count byte (the low byte of the count), flag byte, sort key. There are **five filters**, cycled by -10 (add one) and -11 (subtract one) with wraparound (`FUN_0025e838`), starting at 0 on entry: the five stubs at 0x25e7e0..0x25e830 pass the arguments 0, 0xd, 0xb, 0xc, 0xe, whose words are: everything but spells, abilities and forms (types 0..13, 14, 15, 16, 17, 20), types 0 and 1, types 2..13 (the pair table at 0x3823d0), types 14 and 15, types 16, 17 and 20. The cell text is the item's icon byte and name (`FUN_00284088` through `FUN_00255520`) and a count `*%d` (format at 0x382408) unless the count is 1; the font has no asterisk and its glyph 13 is the multiplication sign, which the port prints [inferred]. An empty list shows "There are no items." (0x45a) in the first cell with group 0x12e (`FUN_0025dae8`). Movement is the grid mover `FUN_00297cc0`: Up and Down move one row, Left and Right wrap inside the row; the port wraps top and bottom on a new press only (the list rule of 1.7) and clamps to the last cell of a short last row [inferred]. Confirm opens page 0xb (not offered on an empty list, `FUN_0025b2a0` clears the mask's 0x10), cancel goes back to page 1 with the cursor on Stock, -4 closes. The help line is the item's description (`item +0xa`, `FUN_0025ddc0`).
- **Page 0xb**, the prompt for the highlighted item (`FUN_0025bfa8`, built by `FUN_0025bad0`): rows "Use" and "Throw away" (messages 0x456, 0x457 at 0x381090) when the item's type is one of the usable types (0x381060: types 0 and 1, `FUN_0025e8a0`), else only "Throw away". "Throw away" is greyed and refused when the item has no sell price (`item +0xe`, `FUN_0025e928`); the choice rule is `FUN_0025eab0` (Use row of a usable type: use; otherwise throw away if it can be, else refused) with the validity callback `FUN_0025eba8`. The title strip shows the item's own list text (icon, name, count).
- **Page 0xc**, the target list (`FUN_0025c590`, built by `FUN_0025c2c8`): one row "All" (message 0x3944) for the group items (5, 6, 7, 0x83: `FUN_001a1fe0`); one row for the two items that go to one member only (0x112, 0x113: the pair at 0x381068, `FUN_0025e978`); else one row per party member, titled "Use on who?" (0x3943). Confirm asks `FUN_0025e9e8` = `FUN_001a14c8` = **`FUN_001a15a0`** whether the item would change anything on the member (any of the four slots for a group item). If it would not: sound kind 8 and page 0xd. If it would: sound kind 0x11, **`FUN_0025ea40` = `FUN_001a11a0(item, member, 0, 100)` then `FUN_001a1ba8(item, 100)`** (the effect with no Item Boost, then one off the stock), and back to page 0xa. Cancel goes back to page 0xb, -4 closes the menu.
- **Page 0xd** (`FUN_0025c930`): the notice "{type}{name} will have no effect if used." (message 0x3b90; the two variables are the type's name message through the table at 0x380a60, `FUN_002553c0`, and the item's name) in the information window with an OK row; every key goes back to page 0xc.
- **Page 0xe** (`FUN_0025cba0`, built by `FUN_0025cae8`): "Throw {}{} away?" (0x394f) with the rows No and Yes (messages 0x1fd1, 0x1fd0 at 0x36cf2c, 0x36cf2a); Yes (row 1) runs `FUN_001a1ba8(item, 100)` and returns to page 0xa; No and cancel return to page 0xb.

**The use check, `FUN_001a15a0` [V, oracle].** HP items (1, 2, 5) need HP below the maximum; MP items (3, 6) need MP below the maximum or the MP charge running; the combined items (4, 7, 0x83) are usable unless HP is full and neither the charge runs nor MP is below full; 0x112 and 0x113 need the drive points below the maximum; the stat boosts (0x114 strength, 0x115 magic, 0x116 defense, 0x117 AP) need the record byte (`+9`, `+0xa`, `+0xb`, `+8`) not above 99 (`FUN_001a0ec0`, `0ee0`, `0f00`, `0f20`); everything else is "no effect". **The boosts' effect** (`FUN_001a0ce0`, `0d30`, `0d80`, `0dd0`): the record byte plus the amount, held at 100 (when the sum would pass 100 only the room is added); the live status block gets the same amount, which the app recomputes from the record (the Status page reads it: after one Power Boost the strength shows 6 where the new game shows 5). The amount is the item's `Flag1 | Rank << 8` word, which is 1 for all four [inferred: the decompilation dropped the argument; the item text says "+1"].

- `item_pages::tests::stock_list_matches_the_game`: `FUN_00283a70` with the five stubs' arguments (and argument 10, see section 14) and `FUN_002845a0` on a party block with counts, against `stock`: `oracle: FUN_00283a70 + FUN_002845a0 equal for 18 lists (1116 entries ...)`.

## 22. Donald and Goofy on the Items and Equipment pages (WP-PM1)

**The party object.** Page 1, the target list of Use (page 0xc) and the equipment list read the party object `DAT_0036ce90`: `FUN_00282940` is its row count (the word at `+0`), `FUN_002829f0(row)` the member id of a row (the u16 at `row * 0x14 + 6`, 0 outside the count) and `FUN_00282980(row)` the row's name word (`+0xc`). `FUN_0025c2c8` builds one target row per party row (a group item shows the single row "All", message 0x3944; an item that goes to one member only shows one row). `FUN_0025e9e8(row)` asks `FUN_001a14c8(item, member of the row)`; for a group item `FUN_001a14c8` answers true when any of the four slots passes `FUN_001a15a0`. `FUN_0025ea40(row)` runs `FUN_001a11a0(item, member, 0, 100)` (a group item loops the four slots), then `FUN_001a1ba8(item, 100)` and `FUN_0013dac8`.
**What the port does.** `ItemsMenu::party` holds the rows when page 1 opens: Sora, then the field members by party slot (`PartyMember::slot`, two at most, as the page 0 cards). Page 1 lists a row per member and the Stock after them (the NEW tag follows the Stock row); the member names are the messages of the table at 0x37ba90 (Sora keeps the literal the page always drew). The preview window shows the highlighted member's record (`Progress::member`). The target page has a row per member; `Snapshot::would_help` is `FUN_0025e9e8` (one `can_use` per member, "All" = any member). The use applies `items::item_effect` to the member's live HP, MP and MP charge (`PartyMember`), the boosts to his record byte (`Progress::apply_boost(member, ..)`), and takes one item. `FUN_001a15a0` has no check for a down member and `FUN_001a12a0` heals through a virtual call on his object (`FUN_001a0140`, `+0x24c`, vtable `+0x78`) whose revive rule was not read [GAP]. So the port never spends an item for nothing: a down member is offered only the boosts (they write the record), "All" needs a standing member that can use it, and the heal leaves a down member alone [inferred; test `a_down_member_is_never_offered_an_item_that_would_be_spent_for_nothing`]. Log lines: `menu: item used: <item> (id N, row K) on member <neo> (<model>): HP a -> b, MP c -> d`; Sora's line is unchanged.
**"Healed Party Members" is not counted by the menu.** `FUN_0025ea40` drops `FUN_001a11a0`'s answer and calls no counter. `FUN_001d76a0` (the counter) has one caller, `FUN_001b8658` (the field command's finish, `items.rs` `use_on_members`), found by scanning the decomp for `FUN_001d76a0(`; so the brief's "count when the target is another member" holds for the field command only and the menu adds nothing.
**Equipment.** Page 2 opens for the member of the row that was confirmed (`ItemsMenu::member`, an index into `party`). The rows are his record (`Progress::member`): the main weapon (`+0`), the armor, accessory and battle-item slots; the drive forms' rows are Sora's (`FUN_00282bf8` asks the drive forms). The weapon page lists the type the pair table 0x3823d0 names for the member (Sora 2, Donald and Goofy the pairs read from the table, `ExeTables::filter_bits`). Every writer takes the member (`equip_weapon`, `equip_armor`, `equip_accessory`, `equip_battle_item`, `set_auto_reload`, `settle_battle_items`); the live `Abilities` block is refreshed only for Sora. -10 and -11 (`FUN_00269580` -> `FUN_0026cfc8(param == -10)`) step the member forward (-10) or back (-11), wrapping at both ends, and write the new row to the remembered cursor of page 1 with scroll 0; the port restarts the list at its first row and plays the cursor sound [inferred].
**AP of members.** `FUN_0019f920` builds status `+0x18e` as the AP of the member's `lvup` row (`FUN_001b50c0`: the table by member id, the first table when his own is missing) plus the record byte `+8` plus the equipped items' AP; `member_ap_max` ports it and the accessory swap check uses it for Donald and Goofy (test `a_members_ap_maximum_is_his_lvup_row_plus_the_record_byte_plus_the_gear`). Whether a member's row 7 of `lvup` is the table's `Ap` field is read from the field list of the table (`Exp Strength Magic Defense Ap ...`).
**Status.** Donald's and Goofy's tabs and the L1/R1 tab step already exist (section 19.1, WP-MN7); nothing was added here.
**WP-PL2 (party follow-ups).** (1) Items on a down member. `FUN_001a15a0` has no KO test (HP below the maximum is true at HP 0), so a down member is offered the heals; WP-PM1b's refusal assumed a revive rule nobody had read. The effect `FUN_001a12a0` reaches the HP through `FUN_001a0140`, a call of vtable `+0x78` of the object stored at the status block's `+0x24c`. The writers of `+0x24c` are the constructors `FUN_00176e00` / `FUN_00176f88` (the player class, vtable `0x35c9a8`, `+0x78` = `FUN_001792f0`) and `FUN_0017c718` / `FUN_0017c840` (the friend class of Donald and Goofy, vtable `0x35cc18`, `+0x78` = `FUN_00176c98`, which calls `FUN_00186238`); the table slots were read from the executable. For a member (flag `+0x588` bit `0x4000`) `FUN_00186238` with a heal above 0 on an object whose `+0x7f8` bit 4 (KO) is set calls `FUN_0017cee8`: the bit is cleared, the motion 0x36 ends, the amount is scaled by `sstm` +0x54, and the HP is added; so an item revives a KO'd member with the scaled amount. The port: `use_on_member` runs `item_effect` on his vitals and gives the HP gain to `party_battle::hp_change` (the same function as the member's own heals), the party tick gets him up. Tests `a_down_member_is_offered_the_heals_as_the_use_check_has_no_ko_test`, `an_item_revives_a_ko_member_through_the_hp_method`. The MP part of Elixirs reaches `FUN_001a0210` (also through `+0x24c`); the port applies it on the live MP as before. (2) Drive Recovery (0x112, 0x113): `FUN_001a15a0` compares the gauge bytes `+0x1b1 < +0x1b2` and `FUN_001a12a0` calls `FUN_001a0290(block, amount * 100)` on those bytes directly, with no HP method and no KO test; the pair has the single Sora row (`FUN_0025c2c8`), who is never down in the menu, so no member can be its target and the port needs no change [the brief's wording "usable on a down member" has no case in the original]. (3) Dodge Roll: the USA executable has no such ability or save field (docs/systems/combat-effects/abilities.md, docs/systems/foundations/final-mix.md); in Final Mix it is an ability in the party record's ability list, which lies inside the range the save body copies (`0x33e860..0x349d40`), so the original brings it back with the body and the port's `dodge_roll` key in the slot file does the same: no change, recorded. (4) The party record sync (`party_record_sync`) no longer overwrites a record that was replaced while the members stand: it writes a member's values only when they changed since its last pass, so Continue's restored allies' HP and MP (the record is replaced at the screen's close, the jump follows a fade later) are the ones the members are rebuilt from. Test `a_replaced_record_is_not_overwritten_by_unchanged_live_vitals`. (5) `track_area` stores a snapshot and a body: test `track_area_stores_the_snapshot_and_a_save_body`.
**Gaps.** The target page does not draw HP/MP bars per row (neither did Sora's single row). (A KO'd member's revive by an item: done in WP-PL2, below.) The preview window's category icons for armor and accessory rows are as for Sora (section 13).
